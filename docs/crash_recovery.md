# 崩溃恢复：一次行动是一个事务

## 问题（先复现，再动手）

一次玩家行动会碰几处持久化的东西：**世界存档**（时间、线索、谁在哪）是权威状态；**NPC 记忆文件、共享设定**是旁边的副作用文件。
记忆是**即时追加**的，世界存档却要等一次行动结束才写。进程在中间被杀，重启后：

```
世界存档：  没见过绫华、会话数 0、没有任何线索
绫华的记忆：「我与旅行者谈了3轮，对方举止得体，值得信赖。」   ← 还会被塞进她下次的提示词（"上次见面"）
```

这是一次**故意的故障注入**发现的（让引擎在"记忆已写、存档未写"时崩），不是线上事故。

## 判断：续跑还是跳过？这里是"回滚"

| 副作用 | 崩了之后 | 为什么 |
|---|---|---|
| 世界状态（线索、进度、NPC 去哪） | 随存档：没提交 = 没发生 | 它们在内存里，只有存档才落盘 |
| 记忆文件、共享设定 | **回滚到行动开始之前** | 内容来自模型，没法让它再说出同一句话；回到行动之前，玩家把这一步重做一遍是安全的 |
| 对外、不可撤销的副作用（发消息、扣款、建工单） | **不能靠回滚**：幂等键 + 先问下游"落地了吗" | 本游戏没有这类副作用，下面"没做的"一节说清楚 |

"玩家说出发"只是**意图**；NPC 说出口的 `go_to`、`tell` 要经过代码校验、由 `physical.set_plan` / `send` 执行才算数，而这些都是世界状态，随存档一起提交。
NPC 的工具循环里的工具（ls / read / recall_memory / lookup_lore / load_skill / respond）全是只读的，没有副作用，崩了直接重来。

## 做法：写前日志（undo log）+ 唯一的提交点

`core/uow.py`（不依赖游戏任何东西）：

1. 行动里**第一次**要写某个文件之前，先把它原样备份（文件当时不存在也记下），并把"正在进行的事务号"原子地落盘。
2. 行动结束 `commit`：先把**世界存档**原子地写下去（里面带着事务号 `tx`），再清掉备份。
3. 重启时 `recover`（在加载任何记忆之前）：
   - 存档里的 `tx` ≥ 日志里的事务号 → 已经提交（崩在"存档写完、备份没清"）→ 只清理；
   - 否则 → 没提交 → 把备份还原，等于它从没发生。还原每一步都可重复，恢复过程中再崩也没关系。

引擎里一次行动（地点层循环的一轮，包括整段谈话）是一个事务，`GameEngine.save()` 就是提交点；`MemoryStore` 每次写文件前先 `touch`。

## 怎么验证：崩溃矩阵（`tests/crash_harness.py`、`tests/test_crash_recovery.py`）

1. **崩溃点**：在副作用的前后放 `crashpoints.hit("名字")`（平时什么都不做）。`SimulatedCrash` 继承 `BaseException`，不会被代码里随手一个 `except Exception` 吞掉。
2. **基线**：不崩跑一遍，每次提交后记下磁盘指纹（存档 + 各记忆文件，去掉墙钟 `ts`），同时记下每个崩溃点被经过几次。
3. **矩阵**：对每个（崩溃点，第 n 次）崩一次——这个场景一共 15 个，**全部枚举，不抽样**——重启后：
   - 磁盘指纹必须**等于基线里存档记着的那次提交**的指纹；
   - 跨文件不变量成立（记忆里有"见过面"，世界里就必须有见面次数）；
   - 日志清干净；
   - 还能接着玩，接着玩之后仍然一致。
4. **反向对照**：把恢复关掉，同样的检查**必须失败**（报出"绫华的记忆文件和那次提交不一致"）。没有这条，上面全过也证明不了什么。
5. 覆盖检查：基线里崩溃点的集合变了（有人新加了副作用点）测试会红，逼你更新矩阵。

## 换到别的 agent 游戏怎么复用

1. 把"权威状态的写盘"包进 `UnitOfWork.commit(persist)`，`persist(tx)` 里把 `tx` 一起存进去；
2. 每个会写旁边文件的存储，写之前调用 `uow.touch(path)`；启动时**先** `UnitOfWork(dir, committed_tx=存档里的 tx).recover()`，再加载那些文件；
3. 在副作用前后放 `crashpoints.hit(...)`；
4. 抄 `tests/crash_harness.py`，实现 `make_engine`（确定性的模型替身 + 固定脚本）、`fingerprint`、`consistent` 三样。

## 没做的（别当成已经解决了）

- **不可撤销的对外副作用**。回滚只对"自己拥有的文件"有效。发消息、扣款这类，应该是：每个副作用步骤有**步骤号 + 幂等键**，
  执行前先写"我要做 X"，做完写"X 已提交"；恢复时遇到"开始了但没提交"的，**不盲目重试**，拿幂等键去问下游"落地了吗"：
  落地了就补记并跳过；下游不能查、工具又不幂等，就停下来人工处理或补偿。本游戏没有这类副作用，所以这一层只写了设计，没写代码。
- **多文件的原子性**靠"备份 + 存档里的事务号"实现，不是真正的数据库事务；同一个存档同时被两个进程写不在保护范围内。
- **trace 日志**是只追加的诊断记录，不参与事务（崩了会多出一段没提交的记录，无害）。
- 崩在**恢复本身**的中途是安全的（还原可重复），但这一条我没有专门注入测试。
