# 崩溃恢复：一次行动是一个事务

## 问题（先复现，再动手）

一次玩家行动会碰几处持久化的东西：**世界存档**（时间、线索、谁在哪）是权威状态；**NPC 记忆文件、共享设定**是旁边的副作用文件。
记忆是**即时追加**的，世界存档却要等一次行动结束才写。进程在中间被杀，重启后：

```
世界存档：  没见过这位 NPC、会话数 0、没有任何线索
NPC 的记忆：「我与旅行者谈了3轮，对方举止得体，值得信赖。」   ← 还会被塞进她下次的提示词（"上次见面"）
```

这是一次**故意的故障注入**发现的（让引擎在“记忆已写、存档未写”时崩），不是线上事故。

## 判断：续跑还是跳过？这里是“先回滚”

| 副作用 | 崩了之后 | 为什么 |
|---|---|---|
| 世界状态（线索、进度、NPC 去哪） | 随存档：没提交 = 没发生 | 它们在内存里，只有存档才落盘 |
| 记忆文件、共享设定 | **回滚到行动开始之前** | 内容来自模型，不能让半截的记忆留在磁盘上被下次读到 |
| 对外、不可撤销的副作用（发消息、扣款、建工单） | **不能靠回滚**：幂等键 + 先问下游“落地了吗” | 本游戏没有这类副作用，见最后一节 |

“玩家说出发”只是**意图**；NPC 说出口的 `go_to`、`tell` 要经过代码校验、由 `physical.set_plan` / `send` 执行才算数，而这些都是世界状态，随存档一起提交。
NPC 的工具循环里的工具全是只读的，没有副作用，崩了直接重来。

## 做法：写前日志（undo log）+ 唯一的提交点

`core/uow.py`（不依赖游戏任何东西）：

1. 行动里**第一次**要写某个文件之前，先把它原样备份（文件当时不存在也记下），并把“正在进行的事务号”原子地落盘。
2. 行动结束 `commit`：先把**世界存档**原子地写下去（里面带着事务号 `tx`），再清掉备份。
3. 重启时 `recover`（在加载任何记忆之前）：
   - 存档里的 `tx` ≥ 日志里的事务号 → 已经提交（崩在“存档写完、备份没清”）→ 只清理；
   - 否则 → 没提交 → 把备份还原，等于它从没发生。还原每一步都可重复，恢复过程中再崩也没关系。

引擎里一次行动（地点层循环的一轮，包括整段谈话）是一个事务，`GameEngine.save()` 就是提交点；`MemoryStore` 每次写文件前先 `touch`。

## ReAct 循环和 RAG 跟恢复是什么关系

NPC 一句回复的核心是一个**有边界的 ReAct 循环**（`core/agent_loop.py`）：每一步模型输出 `{thought, tool, args}`，调用工具拿到观察，直到调用终止工具 `respond`。
工具里最有分量的是两个 **RAG**（检索增强）：

| 工具 | 检索什么 | 怎么检索 |
|---|---|---|
| `recall_memory` | 这个 NPC 自己的长期记忆（含共享设定） | 汉字二元切片的 BM25 + 重要度 + 近因（按“最近一次被用到”算），取前几条 |
| `lookup_lore` | 世界的风物、人物、制度设定 | 同一个 BM25，对设定文档切块 |
| `ls` / `read` | 按角色“知道什么”过滤的上下文文件系统 | 路径浏览，每个人只看得到自己知道的那部分 |

这套结构让恢复变得**很简单**：

1. **循环里没有副作用。**工具全是只读的；`respond` 只交付台词，不改世界。世界变化（给线索、推进幕、NPC 去别处、写记忆）都在循环**之后**由代码校验并落地。所以崩在循环的任何一步，都只是丢掉本轮的临时步骤，回到上一次提交重来。
2. **循环不是状态的载体。**“观察”只留在本轮，跨轮只保留最终回复；剧情状态在 `GodEnv` / 存档里，不靠上下文记。没有“从第几步续跑”的问题。
3. **检索索引是派生物。**BM25 索引由 JSONL 现场建，写入后作废、下次再建，不需要恢复。

**一个要老实交代的细节：RAG 的“读”并不纯。**检索到的记忆会被标成“刚被用到”（`accessed`），这是内存里的写。它被攒着，只在提交时随存档一起落盘（`MemoryStore.flush` 在提交里调用，同样先过 `touch`）。
所以崩在循环中间，磁盘上没有任何变化——崩溃矩阵里有一条专门的测试钉住它。

如果工具**有**副作用，这个结论就不成立了：每个有副作用的工具调用都得带步骤号和幂等键、先记意图再执行。本项目选择**不让模型直接调用有副作用的工具**——模型只“提议”，代码执行——这样恢复才只需要管代码这一层。

## 回滚之后：行动日志让重新跑一遍不白花钱、不换说法

回滚到行动开始之前，状态是对的，但模型已经说过的话、玩家已经做过的选择都没了——模型没法再说出同一句话，玩家也得把这一步重新点一遍。所以回滚之后还有一层**行动日志**（`core/journal.py`）。

它**不是检查点**：没有“跳过有副作用的节点”这回事。有副作用的节点照常重新执行、照常走事务、只在存档那一个提交点上生效；日志只让它们拿到和上次一样的输入。

- **记什么**：`(种类, 请求内容的哈希) → 答案`，三类——模型调用、便宜判定、玩家的选择。文件是只追加的 JSONL，每条 fsync，最后一行写到一半就忽略它。
- **怎么用**：回滚后同一段代码重新执行，遇到“问法一字不差”的请求，直接用当时的答案，其余照常现问。玩家的选择按顺序用，每次连同当时的选项一起校验，对不上就从那里起全部交还给玩家。
  NPC 的随机数状态记在日志头里，接上时放回去（否则“挑哪句告别语”会和上次不同）。
- **为什么安全**：按**内容**命中，所以日志永远不会让代码拿到别的问题的答案；世界、代码、随机数哪里不一样，请求就变，自然未命中、退回现问——**最坏情况就是没有日志**。
- **生命周期**：日志绑定事务号；事务提交了（存档里的号 ≥ 日志的号）日志就过期、丢弃。`RESUME_AFTER_CRASH=0` 关掉 = 回滚后全部现问。
- **接在哪**：模型、便宜判定器、玩家各包一层（`engine/journaled.py`），位置在录制（trace）的里面，命中日志的调用照常出现在 trace 里。

## 怎么验证

### 崩溃矩阵（`tests/crash_harness.py`、`tests/test_crash_recovery.py`）

1. **崩溃点**：在副作用的前后放 `crashpoints.hit("名字")`（平时什么都不做）。`SimulatedCrash` 继承 `BaseException`，不会被代码里随手一个 `except Exception` 吞掉。
2. **基线**：不崩跑一遍，每次提交后记下磁盘指纹（存档 + 各记忆文件，去掉墙钟 `ts`），同时记下每个崩溃点被经过几次。
3. **矩阵**：对每个（崩溃点，第 n 次）崩一次——一共 158 个（含 ReAct 循环中间的两类点、一轮对话的 18 个节点边界、行动日志的每次追加之后），**全部枚举，不抽样**——重启后：
   - 磁盘指纹必须**等于基线里存档记着的那次提交**的指纹；
   - 跨文件不变量成立（记忆里有“见过面”，世界里就必须有见面次数）；
   - 日志清干净；
   - 还能接着玩，接着玩之后仍然一致。
4. **反向对照**：把恢复关掉，同样的检查**必须失败**。没有这条，上面全过也证明不了什么。
5. **覆盖检查**：基线里崩溃点的集合变了（有人新加了副作用点）测试会红，逼你更新矩阵。

### 续跑矩阵（`tests/test_resume.py`）

对同样的 158 个场景：先回滚到最后一次提交，再接着走，**日志里的每一条记录都被用上**（用上的条数 = 重启时日志里的条数，说明重跑和上次逐字相同），最后一致、日志清掉。另有：
崩在一次谈话中间，之前每一轮说过的话一字不差、玩家的选择和模型调用都没有重来；反向对照（关掉日志，同一处崩溃，要整步重来、发的请求更多）；
请求内容变了就一条都不命中、全部现问、仍然一致；选项变了就停止代替玩家选择；日志文件本身（撕掉的最后一行、过期的事务号、同样的请求按顺序各用一次、提交后清掉）。

## 换到别的 agent 游戏怎么复用

1. 把“权威状态的写盘”包进 `UnitOfWork.commit(persist)`，`persist(tx)` 里把 `tx` 一起存进去；
2. 每个会写旁边文件的存储，写之前调用 `uow.touch(path)`；启动时**先** `UnitOfWork(dir, committed_tx=存档里的 tx).recover()`，再加载那些文件；
3. 在副作用前后放 `crashpoints.hit(...)`；
4. 抄 `tests/crash_harness.py`，实现 `make_engine`（确定性的模型替身 + 固定脚本）、`fingerprint`、`consistent` 三样；
5. 想要“问过的不重问”，再包一层 `core/journal.py`（`Journal` 本身不依赖游戏，接线看 `engine/journaled.py`）。

## 面试回答（口述版，约 2 分钟；方括号换成你的真实表述）

> 我们做的是一个文字调查游戏里的 NPC agent，核心是一个有边界的 ReAct 循环：模型每步输出思考、工具和参数，工具主要是两个 RAG——查 NPC 自己的长期记忆、查世界设定——都是只读的，最后调用 respond 交付台词。**模型只提议，副作用由代码执行。**
>
> 我没有线上崩溃的案例，这个问题是我**主动做故障注入**发现的：我想验证“玩家说出发”这种意图什么时候才算真的发生。一次行动会碰两类持久化——世界存档是权威状态，NPC 的记忆文件是旁边的副作用，而且记忆是**即时追加**的、存档要等行动结束才写。我在“记忆已写、存档未写”时杀进程，重启后世界说“没见过面”，NPC 的记忆里却写着“我们谈了三轮”，还会被塞进下次的提示词。
>
> 续跑还是跳过，我是按**副作用归谁**来判断的：世界状态没提交就等于没发生，所以**先回滚**，回到行动开始之前，有副作用的节点一个都不跳。记忆内容来自模型、没法让它重新说出同一句话——这一点我后来补了一层行动日志：回滚之后重新跑，问过的模型调用和玩家做过的选择按请求内容命中，原样用上，不命中就现问。真正对外、不可撤销的副作用（发消息、扣款）不能靠回滚，要用幂等键、先写意图再执行、恢复时对“开始了没提交”的先问下游——**这一层我只做了设计，这个项目里没有这类副作用，所以没实现。**
>
> 改法是写前日志：行动里第一次写某个文件前先备份，世界存档是唯一的提交点、里面带事务号；重启时先恢复再加载，没提交的还原，已提交的只清理。验证用崩溃矩阵：在副作用前后放崩溃点，把这个场景里**全部 158 个**（崩溃点 × 第几次经过）各崩一次——包括 ReAct 循环中间和一轮对话的每个节点之间——重启后磁盘指纹必须等于最后一次提交，还要能接着玩；另外做了**反向对照**：关掉恢复，同样的检查必须失败，证明检查看得见原来的 bug。

被追问时的准备：
- **“开始了但没提交的怎么办？”**——对自己拥有的文件：回滚；对外部系统：幂等键 + 查询下游，查不到就停下来人工或补偿。
- **“RAG 的读有副作用吗？”**——有一个：检索会标记“最近被用到”，攒在内存里随提交落盘，崩了不残留，有测试。
- **“模型不确定，重放时选了别的工具怎么办？”**——恢复分两层。状态那层**不重放模型**：回滚到行动之前。其上是行动日志：按**请求内容的哈希**记着，问法一字不差才用当时的答案——所以不会拿到别的问题的答案，世界或代码变了就自然未命中、现问。调试重放（`tools/replay_game.py`）是另一回事，是为了复现。
- **“并发呢？”**——同一个存档被两个进程写不在保护范围内，这是我划的边界。

## 没做的（别当成已经解决了）

- **不可撤销的对外副作用**。回滚只对“自己拥有的文件”有效。发消息、扣款这类，应该是：每个副作用步骤有**步骤号 + 幂等键**，
  执行前先写“我要做 X”，做完写“X 已提交”；恢复时遇到“开始了但没提交”的，**不盲目重试**，拿幂等键去问下游“落地了吗”：
  落地了就补记并跳过；下游不能查、工具又不幂等，就停下来人工处理或补偿。本游戏没有这类副作用，所以这一层只写了设计，没写代码。
- **多文件的原子性**靠“备份 + 存档里的事务号”实现，不是真正的数据库事务；同一个存档同时被两个进程写不在保护范围内。
- **trace 日志**是只追加的诊断记录，不参与事务（崩了会多出一段没提交的记录，无害）。
- 崩在**恢复本身**的中途是安全的（还原可重复），但这一条没有专门注入测试。
- 并行判定开着时，日志只在“请求内容命中”这一层容忍乱序，没有为它单独做崩溃注入。
